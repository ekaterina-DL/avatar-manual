# Дизайн: устранение дублей и визуальная система для мануала 2 этапа

Статус: утверждено пользователем 11.08.2026, готово к переходу в implementation-план.

## Зачем

В 2 этапе (`manual-2-etap/00-09.md`) одни и те же факты — длина сегмента, порог молчания, правило
зума, проверка перед «Битое» и т.д. — сформулированы в нескольких файлах независимо друг от
друга. Это не просто громоздко: один случай — уже реальная рассинхронизация. Порог молчания
(3-4 сек / памятка 2-3 сек) как нерешённая вилка повторён в `01`, `02` и `05`, при этом
`09-disputed-points.md` уже **практически решил** этот вопрос точнее (2-3 сек на границах
сегмента, 3-5 сек внутри — подтверждено заказчиком дважды), но уточнённое значение не попало
обратно в канонические разделы. Асессор, читающий `01` или `05`, видит только старую нерешённую
пару значений.

Дополнительно пользователь хочет визуально современную подачу: эмодзи по смыслу тем, цветовые
статус-плашки и градиентные шкалы порогов, блок-схемы для решений с вложенным if/else
(«Сегмент или „Битое“?», «Сколько сегментов выделять», «Резать по молчанию или нет»).

**Отличие от предыдущего дизайна** (`2026-08-07-site-content-restructure-design.md`, там было
жёсткое ограничение «файлы manual-2-etap не редактируются»): в этом заходе правки идут прямо в
файлы мануала — дедуп по определению требует менять содержание, а не только упаковку сборки.

## Модель дедупа: один канонический «дом» на факт

Для каждого факта — ровно одно место, где он сформулирован полностью, с нюансами и источником.
Всюду, где факт упоминался раньше, остаётся короткая ссылка на канонический дом без повторения
цифр/формулировок.

| Тема | Канонический дом | Что становится ссылкой |
|---|---|---|
| Длина сегмента (10–300 сек) + погран. случаи | `02-segments.md` | Термин в `00-overview.md`, чек-лист-пункты в `05-what-to-label.md` |
| Молчание — порог | `02-segments.md` (уточнённое значение: 2-3 сек на границах / 3-5 сек внутри, из `09-disputed-points.md`) | `01-general-requirements.md`, `05-what-to-label.md` |
| Зум (резкий/плавный) | `02-segments.md`, раздел «Определение и границы» (убрать второе внутреннее повторение в разделе «Сколько сегментов») | `08-lifehacks.md` — оставляет только практический приём, без повтора правила |
| Проверка перед «Битое» | `02-segments.md` | `05-what-to-label.md` |
| Фокус на лице | `01-general-requirements.md` | `05-what-to-label.md` |
| Техническое качество (разрешение, пиксельность, FPS) | `03-video-quality.md` | без изменений — самостоятельный угол, не дубль |

файлами — коротким пересказом со ссылками, а не вторым источником цифр.

## Визуальная система

**Принцип PDF/сайт:** эмодзи в заголовках — плейн-текст, работает одинаково в PDF и на сайте.
Цветные плашки-статусы и блок-схемы — только сайт; в PDF остаётся чистый текст/список (тот же
принцип, что уже в `build_dispute_flow.py` и `hide_site_only_sections.py`).

1. **Эмодзи по темам** — один эмодзи на тему, используется в заголовках канонического файла и
   везде, где на тему коротко ссылаются: `⏱️ Длительность` · `🔇 Молчание` · `✂️ Склейки` ·
   `👤 Лицо` · `🎥 Тех. качество` · `🎭 Классификатор` · `🚫 Битое`. ⚠️ для предупреждений/
   расхождений — уже используется, не меняется.

2. **Статус-плашки в `09-disputed-points.md`** — 🟢 Решено / 🟡 Частично решено / 🔴 Не решено
   вместо текстовой строки «Статус: …» в прозе.

3. **Градиентная шкала** для порогов с несколькими уровнями (пример — молчание: 0–2 сек ок →
   2–3 сек граница сегмента → 3–5 сек внутри допустимо → больше — резать). Прямой HTML-блок в
   каноническом файле (через уже подключённый `md_in_html`), не отдельный хук — таких шкал мало,
   генератор избыточен.

4. **Блок-схемы** для вложенных if/else-решений: «Сегмент или „Битое“?», «Сколько сегментов
   выделять» (однотипные / разные / длинная сцена), «Резать по молчанию или нет» (короткая пауза
   vs длительное молчание). По образцу уже существующей схемы апелляций в `00-overview.md`.

## Техническая реализация

**Устойчивость новых хуков.** Старые хуки (`shorten_prose.py`, `build_dispute_flow.py`)
матчатся на точный текст целиком — любая будущая правка прозы их молча ломает (это
задокументированная и уже подтверждённая на практике проблема из прошлой сессии). Новые хуки
матчатся **по заголовку раздела + структуре** (список/таблица под ним), как уже сделано в
`build_segment_examples.py` и `build_compare_cards.py` — переживёт правки формулировок.

**Новое в `site/`:**
- `site/hooks/build_status_badges.py` — статус (`Решено`/`Частично решено`/`Не решено`) в
  `09-disputed-points.md` → цветная плашка.
- 2-3 CSS-класса в `site/theme/extra.css` для градиентной шкалы и статус-плашек.
- Флоучарты по образцу `build_dispute_flow.py`, но матчинг по заголовку раздела, не по точному
  тексту целиком.

**Устаревающие записи `shorten_prose.py`** (относящиеся к `00-overview.md`/`02-segments.md`)
убираются по мере того, как соответствующий текст переезжает в чистом виде прямо в канонический
файл — сокращать станет нечего, хук и так no-op, но лучше без мёртвого кода.

## Addendum (11.08.2026) — Волна 3: финальные решения по статус-плашкам

Реальный текст `09-disputed-points.md` (17 пунктов) оказался куда разнообразнее, чем строгая
пара «решено/не решено» — часть пунктов сформулирована как «практически решено», «не решено
формально, но практика стабильна», «скорее всего не проблема» и т.п. Ниже — финальные решения,
подтверждённые пользователем, без которых нельзя написать план без «заглушек».

**Принцип классификации на 3 канонических значения:**
- 🟢 **Решено** — правило подтверждено официальным документом или прямой цитатой заказчика,
  противоречий не осталось.
- 🟡 **Частично решено** — официальный текст инструкции/памятки формально не менялся, но есть
  **прямое подтверждение источника заказчика** (переписка, ОС, реальная практика заказчика) —
  не просто мнение команды в внутреннем чате.
- 🔴 **Не решено** — либо прямое противоречие источников, либо единственное свидетельство —
  мнение/рабочая гипотеза команды без подтверждения заказчиком напрямую (даже если команда
  единодушна).

**Итоговая классификация всех 17 пунктов** (текущий текст → куда встаёт лейбл):

| # | Раздел (по порядку в файле) | Плашка |
|---|---|---|
| 1 | Диалог: взаимный разговор или два человека в кадре | 🔴 Не решено |
| 2 | Смена эмоций — нужна ли склейка для разделения | 🔴 Не решено |
| 3 | Длительность молчания внутри сегмента | 🟡 Частично решено |
| 4 | Сколько сегментов при однотипных фрагментах | 🟡 Частично решено |
| 5 | Максимальная длина исходного видео | 🟢 Решено |
| 6 | Объединение сегментов через склейку | 🔴 Не решено |
| 7 | Моно-звук [РЕШЕНО] | 🟢 Решено |
| 8 | «До пояса» в позе тела [РЕШЕНО] | 🟢 Решено |
| 9 | Виньетка ⚠️ РЕШЕНО (сейчас без строки «Статус:» — добавляется) | 🟢 Решено |
| 10 | Тряска/гуляние камеры | 🔴 Не решено |
| 11 | Кратковременное торможение кадра | 🔴 Не решено |
| 12 | Очки, скрывающие глаза | 🔴 Не решено |
| 13 | Человек смотрит вниз | 🔴 Не решено |
| 14 | Половина лица в тени | 🔴 Не решено |
| 15 | Вид из окна машины зимой | 🟡 Частично решено |
| 16 | Пиксельность лица / размытые руки | 🔴 Не решено |
| 17 | Наложенный текст в кадре | 🔴 Не решено |

**Техническое решение:**
- Каждая строка «Статус: …» нормализуется так, чтобы начинаться ровно с одного из 3
  канонических жирных ярлыков — `**Решено**` / `**Частично решено**` / `**Не решено**` — сразу
  после которого текст пояснения остаётся как есть (факты/даты/цитаты не меняются, меняется
  только вступительная фраза). Формат совпадает с уже задекларированным в шапке файла шаблоном
  («Формат записи»), который до этой волны не соблюдался единообразно; сам шаблон-пример тоже
  обновляется, но с ``бэктиками`` вместо `**bold**`, чтобы не совпасть с regex хука.
- Пункт 9 (Виньетка) — добавляется новая строка `- Статус: **Решено** — см. прямой ответ
  заказчика выше (07.08.2026).`, которой сейчас нет вовсе.
- Новый хук `site/hooks/build_status_badges.py` матчится по фиксированному словарю (regex
  `^- Статус: \*\*(Решено|Частично решено|Не решено)\*\*` в начале строки), не по всему тексту —
  устойчиво к будущим правкам пояснений. Точечные «Статус:» внутри других пунктов (например,
  вложенное замечание про точную границу 10:00 в разделе про макс. длину видео) не матчатся, т.к.
  не стоят в начале строки после `- `.
- Цвета — переиспользуются существующие CSS-переменные (`--ok-color`/`--ok-bg` для 🟢,
  `--no-color`/`--no-bg` для 🔴, `--accent-ink`/`--accent-bg` для 🟡) — новых токенов не вводится.
- Заголовки разделов (`⚠️ НОВОЕ`, `[РЕШЕНО]`, `⚠️ РЕШЕНО`) не трогаются совсем — избегаем риска
  сломать якоря; плашка в теле пункта становится основным сигналом, лёгкая избыточность с
  заголовком — осознанно принятый компромисс.
- PDF-профиль (`is_pdf_build`) хук не трогает — там остаётся обычный текст «Статус: **Решено**
  — ...» без HTML.

После каждого файла (как и с `00-overview.md` в прошлой сессии):
1. `pytest site/hooks/tests/` — все тесты зелёные.
2. Сравнение сборки `mkdocs build` до/после правки (git stash/pop) — не появляются новые
   предупреждения о битых ссылках/якорях.
3. План + диф показывается пользователю на подтверждение **до** правки следующего файла.

## Addendum (12.08.2026) — градиентная шкала и блок-схема «Сегмент/Битое»

Пункты 3 и 4 «Визуальной системы» (см. выше) были концептуально утверждены 11.08.2026, но без
точных CSS/визуальных деталей — это первый заход, где они прорабатываются и фиксируются.
Обсуждение прошло через визуальный помощник брейнсторминга (мокапы в браузере), пользователь
кликом выбрал конкретные варианты из нескольких показанных.

**Объём этой волны — уже, чем исходные пункты 3-4:**
- Градиентная шкала — **две** штуки, обе в `02-segments.md`: молчание (пример из исходного
  дизайна) и перекрытие рта (второй похожий многоуровневый порог, найденный в том же файле).
- Блок-схема — **только** «Сегмент или „Битое“?». «Сколько сегментов выделять» сознательно **не**
  делаем блок-схемой: при ближайшем рассмотрении это не одна развилка if/else, а 5-6 независимых
  критериев (однотипные/разные, статика/движение, речь/пение, длительная сцена и т.д.) — сжатие в
  блок-схему рискует либо потерять нюансы, либо получиться настолько ветвистой, что будет читаться
  не легче текущего списка; остаётся текстом. «Резать по молчанию или нет» отдельной схемой тоже
  не делаем — это тот же самый порог, что уже визуализирует градиентная шкала молчания, отдельная
  блок-схема была бы дублированием того же факта в другой форме.

**Принцип размещения — только добавление, ничего не убирается.** В отличие от статус-плашек
(волна 3, где плашка заменила строку «Статус: …» — та была чистой тавтологией), здесь визуальный
блок вставляется **после** уже существующего текста и ничего не заменяет — сохраняется требование
проекта «никогда не терять детали». Прямое следствие: PDF ничего не теряет, даже если элемент от
него скрыт (см. ниже) — вся информация и так остаётся текстом на своём месте.

**Отступление от исходного технического плана (стр. «Техническая реализация» выше).** Там для
блок-схем предполагался хук с матчингом по заголовку раздела (по образцу
`build_dispute_flow.py`). Раз элемент теперь **не заменяет** текст, а вставляется рядом с ним, хуку
нечего было бы генерировать под условие — вместо этого решение то же, что уже принято для
градиентной шкалы (пункт 3 исходного дизайна): **прямой HTML-блок в исходном markdown-файле**
(через уже подключённый `md_in_html`), без `markdown="1"` (в тексте блоков нет markdown-разметки,
только текст/эмодзи — по образцу `.apeal-flow`, где `markdown="1"` тоже не использован). Это не
только проще, но и надёжнее хука: не может «молча перестать матчиться» после будущей правки прозы
(документированная и уже дважды всплывавшая в проекте проблема с `shorten_prose.py`/матчингом по
точному тексту).

### Шкала 1 — 🔇 Молчание (`02-segments.md`, конец раздела «Определение и границы»)

Вставляется сразу после текущей последней строки раздела (`` `[Инстр. Kandinsky-Аватар, стр.2,
10]` ``, сейчас строка 69), перед пустой строкой и заголовком `## Ограничения интерфейса`. Точный
текст самого раздела (списки, цитаты) не меняется ни на символ.

4 деления, схематично (не в реальном пропорциональном масштабе времени — молчание на границе и
внутри сегмента — разные метрики, шкала показывает их последовательно, как и было утверждено в
исходном примере дизайн-документа):

| Деление (метка) | Позиция по X | Цвет заливки трека (в эту точку) |
|---|---|---|
| `0с` | 0% | зелёный (`var(--ok-color)`) начинается |
| `2с` | 35% | зелёный кончается / жёлтый (`var(--md-accent-fg-color)`) начинается |
| `3–5с` | 62% | жёлтый кончается / зелёный снова начинается |
| `>5с` | 78% | зелёный кончается / красный (`var(--no-color)`) начинается, до 100% |

Подписи зон (под треком, по центру своей зоны): «ок везде» (~17%), «граница/внутри» (~48%),
«резать» (~89%) — ровно как в утверждённом пользователем мокапе (вариант B).

### Шкала 2 — 🤐 Перекрытие рта (`02-segments.md`, тот же раздел, сразу после Шкалы 1)

Тот же визуальный компонент (`.threshold-scale`), новые деления — 3 вместо 4 (здесь нет отдельной
«границы сегмента» метрики, только нарастающая критичность):

| Деление (метка) | Позиция по X | Цвет заливки трека (в эту точку) |
|---|---|---|
| `доля сек.` | 0% | зелёный начинается |
| `неск. сек.` | 40% | зелёный кончается / жёлтый начинается |
| `>50% сегмента` | 75% | жёлтый кончается / красный начинается, до 100% |

Подписи зон: «ок» (~20%), «обрезать участок» (~57%), «сегмент целиком не подходит» (~90%).

### CSS

Новые классы в `site/theme/extra.css`:
- `.threshold-scale` (контейнер), `.threshold-scale .ts-caption` (надпись темы, стиль как у
  `.video-block .eyebrow` — Golos Text, uppercase, `--gray-600`), `.ts-track` (сама линия, высота
  8px, `border-radius`, заливка — inline `style="background:linear-gradient(...)"` прямо в HTML
  каждого блока, т.к. у двух шкал разные точки остановки — отдельный CSS-класс под каждую был бы
  избыточен), `.ts-tick` (метка деления над треком + короткая засечка вниз через `::after`),
  `.ts-zone` (подпись зоны под треком). Адаптив: на `max-width: 480px` уменьшить `font-size` и
  ширину `.ts-zone`, чтобы подписи не наезжали друг на друга (риск, отмеченный в самом мокапе
  варианта B).
- `.decision-outcome` (контейнер, `display:grid`, 2 колонки, `@media max-width:560px` → 1
  колонка — тот же паттерн, что уже у `.compare`), `.decision-outcome .do-question` (текст вопроса
  над карточками), `.do-card` + `.do-card.good`/`.bad`, `.do-tag`, `.do-body` — визуально похоже на
  `.compare-card`/`.compare-tag`/`.compare-cap`, но самостоятельный класс (см. обоснование выше).

Новое правило в `site/pdf/pdf-extra.css` (тот же приём, что уже скрывает статус-плашки в PDF):
```css
.threshold-scale,
.decision-outcome {
  display: none;
}
```
PDF в этих местах показывает уже присутствующий рядом полный текст без изменений — ничего не
теряется и не задваивается.
